### V1: Foundry version
The `foundryvtt/pf2e` branches disagree, which is easy to misread:

| Branch | System | Foundry |
|---|---|---|
| `v14-dev` (default branch) | 8.6.1 | min 14.361, verified 14.369 |
| `v13-dev` | 7.12.2 | min 13.348, verified 13.351 |
| `release` / `master` | 6.12.4 | 12.328 to 12.331 (stale) |

The live PF2e line is v14. A first read of `master` suggested v12; that was a stale branch.

**Decision:** support Foundry v13 and v14 (`module.json` min 13, verified 14). Use only ApplicationV2 APIs present in both, and test on both before release.

### V2: Actor and token data (PF2e)
- **HP:** `actor.system.attributes.hp` (`value`, `max`, `temp`).
- **Conditions:** `actor.hasCondition(...slugs)`; `actor.conditions.bySlug(slug, { active: true })`; `actor.conditions.active`. Slugs are PF2e `ConditionSlug` values (`actor/conditions.ts`, `item/condition/values.ts`).
- **Reach:** `actor.getReach({ action: "attack", weapon? })` (`actor/creature/document.ts`). Base reach is `attributes.reach.base`; weapon `reach` traits are considered.
- **Distance:** `token.distanceTo(otherToken, { reach })` (`canvas/token/object.ts`). It measures between squares/cuboids and respects elevation. Passing `reach` makes it reach-aware, so "enemy in melee reach" is `reach >= token.distanceTo(enemy, { reach })`, the same test PF2e uses in `canFlank`. Returns `NaN` if the canvas is not ready.
- **Allies and enemies:** `actor.alliance` is `"party" | "opposition" | null`; `isAllyOf()` and `isEnemyOf()` exist. **Resolves the brief's [OPEN] on "ally":** use PF2e alliance, not token disposition. Note `isEnemyOf` is false if either side is `null`.
- **Strikes:** `actor.system.actions` is `AttackAction[]`. `StrikeData` has `label`, `type: "strike"`, `item`, `ready`, `variants` (MAP variants), `altUsages`. Area/auto-fire entries have `type: "area-fire" | "auto-fire"`.
- **Melee vs ranged (for slot auto-bind):** `strike.item.isMelee` / `isRanged` on both weapon and NPC `melee` items.

### V3: Chat card flags (for auto-detecting actions)
Under `message.flags.pf2e` (`chat-message/data.ts`):
- `context.type`: `"attack-roll"`, `"damage-roll"`, `"spell-cast"`, `"skill-check"`, `"area-fire"`, `"auto-fire"`, `"self-effect"`, `"damage-taken"`.
- `context.actor` and `context.token` identify the actor; `context.item` the item; `origin` has `{ actor, type, uuid }`; `context.target` the target.
- A Strike is an `attack-roll` then a `damage-roll`: **count only the `attack-roll`** or each strike will register twice.
- The stored flag omits `context.action`, but `context.identifier` is `${itemId}.${attackSlug}.${melee|ranged}` for strikes, which tells melee from ranged. Skill-based actions carry an `action:<slug>` entry in `context.options`; plain skill checks do not, so they are not counted.
- Current-combatant test: `message.speaker.token === combatant.tokenId`, falling back to `context.token` (a UUID ending in the token id).
- Movement is not a chat card. Detect via `updateToken` on `x`/`y`.

### V4: Flanking (v1.1)
Available: `token.canFlank(flankee)`, `actor.attributes.flanking.{canFlank, flankable}`. Gated by the PF2e flanking automation setting.

### V7: Action budget
No per-turn action tracking found in PF2e (`encounter/`, `actor/base.ts`). The module keeps its own (`engine/budget.mjs`): base 3, minus slowed and stunned values, plus 1 for quickened, 0 if paralyzed or unconscious. Quickened's action restriction is ignored (GM corrects the log). Condition badge values come from `condition.value`.

### New: turn hooks
PF2e fires `pf2e.startTurn(combatant, encounter, userId)` and `pf2e.endTurn(...)` (`encounter/combatant.ts`) after its own turn-start effects run. Prefer these over raw `combatTurn`. Note `onStartTurn` runs per represented actor for troops.

## Decided

- **Ranking:** rule order is priority; an explicit `priority` (lower first) overrides position; higher `weight` breaks ties. Implemented in `scripts/engine/evaluate.mjs`.
- **"Ally":** PF2e actor alliance (V2). A monster is an `opposition` actor; its enemies are actors for which `isEnemyOf` is true.
- **Reach and distance semantics:** `enemy-in-reach` is a global any-enemy check (negated: no enemy in reach), matching the brief's `volley` rule. `enemy-within` narrows eligible targets. Unknown distance (`null`: canvas not on that scene, token missing, NaN) is excluded from `enemy-within` even when negated, and counts as not-in-reach. Reach test mirrors PF2e's `canFlank`: `reach >= token.distanceTo(target, { reach })`.
- **What "Took it" does:** records every action in the suggestion as taken (source `suggestion`) and records a use of that rule, which is what rule limits count. Auto-detected actions never count as rule uses, because a chat card can't be tied to a rule. After any history change the suggestion is re-evaluated.
- **Limit semantics:** `cooldownRounds: N` after a use in round R makes the rule available again in round R+N. `maxPerTurn` counts uses in the current round. `oncePerEncounter` counts any use.
- **Policy semantics:** `maxSameActionPerTurn` holds back a rule if actions already taken this turn plus the (budget-trimmed) bundle would exceed the cap for any one action key. `stride-away` and `stride` are one key. Provisional default: 2.
- **Bundle vs budget (partial answer to the adaptive-bundle [OPEN]):** the bundle is trimmed to the actions remaining; no "strike x remaining" syntax yet.
- **Storage:** history lives in a Combat flag (`flags.monster-brain.history`), written only by the active GM (`game.users.activeGM`) so two GM clients never double-write.
- **Movement:** any `x`/`y` update to the current monster's token counts as a Stride; updates within 4 s merge into one.
- **Per-token profiles (supersedes the actor-only storage in V6):** behaviour is stored per token, because one actor sheet can back many tokens that need to differ. A token profile is a flag on the TokenDocument; the actor profile (flag on the base actor) remains as an optional default for all of its tokens. Cascade order is now system, campaign, template, creature (actor), **token**, encounter. A token's `template` key replaces the actor's (`null` = no template, absent = inherit). Rules, `disable`, policies and `slotBindings` merge layer over layer as usual.
- **Configure dialog:** opened from a Token HUD button (right-click an NPC token) or `api.configure()`. Lets you pick a template, switch rules off, bind slots, choose scope (this token, default; or every token of the actor), and shows a live dry-run preview of unsaved edits. A rule switched off by a *different* layer is shown but locked, because the cascade can only re-enable a rule by supplying it again. The button placement follows PF2e's own `renderTokenHUD` usage (anchored beside the effects button; verified against the PF2e source, not against Foundry core).
- **Roles dialog:** PC tokens get a tag button on the Token HUD (NPCs get the configure button; `hudKindFor` decides by actor type) and `api.tagRoles()`. Scope is the character's default (always available) or this encounter only (needs a combatant for the token; replaces the default for that fight; "use the default" removes the override). Saving with no tags clears the default rather than storing an empty list, but an empty encounter override is kept (it means "no roles this fight"). Saving during a running combat re-evaluates the strip. Allied NPC tokens (also targetable) cannot be tagged from the HUD yet, only through `setActorRoles` and `setCombatantRoles`.
- **Rule and template editor (build step 8):** `engine/schema.mjs` is the single description of the vocabulary the form offers (conditions and their parameters, actions, target preferences, limits, real PF2e condition slugs); a test fails if a condition exists in the engine without a schema entry. All edits go through immutable functions in `engine/rule-draft.mjs`. The form (`template-editor.mjs`) is a DOM view over them. Starters are read-only (Duplicate to edit); templates live in the world setting, so a saved template of a starter's id overrides it. Shipped default rules can be switched off per template, but not if the template replaces that rule itself (the cascade would then disable the template's own version). Rule ids are generated from the name at creation and never change, so renaming a rule keeps references stable.
- **Editor UI rule:** text and number fields update the draft without re-rendering (otherwise blur would trigger a re-render that swallows a click on Save); structural changes re-render; scroll position is preserved across renders. Custom slot names and role tags are cleaned on blur, not per keystroke, so spaces and hyphens can be typed.
- **Campaign policy UI:** only the repeat cap (`maxSameActionPerTurn`) exists as a policy; "no limit" is stored as `null`, which the cascade treats as removing the policy.
- **Action feasibility: the world model (`engine/world.mjs`) (added after live play):** the engine used to treat every action as always possible, so a Brawler with a *ranged* signature planned "signature, then melee Strike" against someone 60 ft away. Now each rule's action list is *planned* against a target, tracking distance as the turn unfolds. Requirements: a melee Strike (or a signature bound to a melee item or touch spell) needs the target within that weapon's own reach; a ranged Strike (or ranged signature, or spell with a parsed range) needs it within range; Stride closes distance by up to the creature's Speed; Stride away opens it; movement is blocked by grabbed, immobilized, restrained and the incapacitating conditions; a prone creature must Stand up before moving (a Strike can be made prone). What a signature needs comes from the *kind of item it is bound to* (melee/ranged/other), which is why binding it matters.
- **Repair, don't reject (and say so):** when a Strike would be out of reach the plan *adds the Strides it needs* ("Added Stride: Mira is 30 ft away (Melee strike needs 5 ft)"), *skips a Stride that is not needed* ("Skipped Stride: Mira is already adjacent"), *drops a Strike that follows a Stride away* (rather than walking back), and *closes as far as it can and stops* when the gap eats the turn. Only a genuinely impossible plan (can't move and out of reach, can't act at all) is held back, with the exact reason. Every change is listed in `adjustments`, shown on the card and in "Why this one". Considered and rejected: holding back any rule whose authored bundle is not literally possible, which would leave far-away creatures with no suggestion at all.
- **Target choice respects feasibility:** targets are tried in the rule's preference order and the first one the plan works against is used, so a restrained creature skips a preferred far target for one it can hit. Unknown distance (no tokens) cannot be checked, so those steps are assumed possible.
- **Movement is exempt from the repeat cap:** closing a gap can take several Strides; the cap exists to stop "Strike, Strike, Strike". The shipped fallback rule was renamed from "Strike, strike" to "Attack the nearest" because it may now be only walking.
- **New data used (verified in the PF2e source):** `actor.system.movement.speeds.<type>.value` (the fastest type is used, so a flyer's Stride is its Fly speed), `item.reach` / `actor.getReach({ action, weapon })`, `item.range.max` for ranged attacks and spells, `spell.isMelee`. Speed defaults to 25 when unknown. The planner's reach test is a plain distance comparison, so it can differ from PF2e's own `distanceTo(..., { reach })` at diagonal edge cases (the `inReach` flag used by conditions and target preferences still uses PF2e's own measure).
- **Showing the plan, current step highlighted:** the strip shows the action to do now in bold after a marker, then the target, with what follows muted ("▶ Stride → Mira  then Melee strike"). The card lists numbered steps with the current one highlighted (and `aria-current`), marks steps the planner added, and lists adjustments. **"Did this action"** records only the highlighted step; **"Took whole plan"** records all of it. The plan is re-derived after every recorded action, so if the situation changes mid-plan a different rule can take over.
- **Rule uses count completed plans:** with step-by-step recording a rule is counted as used when its *last* step is recorded (or the whole plan is taken at once), not at the first. Otherwise a rule with `maxPerTurn: 1` (e.g. Skirmisher's "strike and fade") would shut itself out of its own second step.
- **A Stride reported twice (click and token drag):** a click ("suggestion"/"manual") and a drag ("auto") for the same Stride within a minute are merged into one, in either order; after a merge the Stride is spent, so a further drag is a new Stride. Two drags on the same side are always separate Strides (a rapid burst within 4 s is still one drag).
- **A plan must advance as steps are recorded (bug found in live play):** the plan used to be re-derived from the rule's *full* action list, with only the budget reduced, so recording "signature" produced the same plan starting with "signature" again. Now `engine/taken.mjs#remainingBundle` takes what was already done this turn off the rule's list before planning (matched by action key and, for movement, by the original slug so a Stride and a Stride away stay distinct; a token drag has no direction and counts toward the first outstanding movement step). A rule whose every action is done is held back as "already done this turn" so the next rule takes over. The repeat cap now sees the same remaining actions, so a half-done rule is no longer shut out by the cap it would have met.
- **Recorded actions change the world model:** a Stride recorded by *clicking* (not merged with a token drag) still moves the creature in the plan, shifting the distance by one Speed toward or away, so clicking "Did this" for a Stride advances the plan even if the token is not moved. A Stride detected from a *drag* does not shift anything (the measured position already reflects it), and neither does a click that was merged with a drag (no double counting). A recorded Stand up clears prone; having moved away this turn, a later Strike is not "repaired" by walking back.
- **A detected roll is recorded as the plan step it fulfilled:** the chat card says which *item* was used (strike identifier prefix, spell `origin.uuid`, self-effect `context.item`). A creature's signature is often one of its Strikes, so one item can fill two slots (the reported case: signature bound to the ranged attack, which is also the auto-bound ranged-strike). `slotForItem` picks, in order: a slot the plan on screen is waiting for (the first step of each suggestion shown, noted by the strip), an explicit GM binding, the generic Strike the roll looked like, the first slot bound to that item. Recorded actions carry a `slug` as well as a `key`.
- **Unknown distance is now visible:** the plan states "Distance to X is unknown (is its token on this scene?), so reach and range were not checked" instead of quietly looking certain; the strip shows the measured distance next to the target ("→ Mira (55 ft)", or "(? ft)") and the card shows "Target: Mira · 55 ft away" or "distance unknown". Cause found for one way distances went unknown: the adapter required `combat.scene` to equal the viewed scene, so a combat with no scene set made every distance unknown. That check is removed; a token is measurable when `TokenDocument#object` exists (it is null unless its scene is viewed). If a 55 ft target still gets a plain Strike first, run `api.explain()` and look at that enemy's `distance` / `inReach` in `ctx.enemies`.
- **Known gap:** limits (cooldown, once per encounter) count a rule as used when its last step is recorded with "Did this action"/"Took whole plan". If the GM finishes a plan only by rolling dice and dragging tokens (all auto-detected), the rule is not counted as used.
- **Cascade layers (build step 3):** a layer is `{ rules?, disable?, policies?, slots?, slotBindings? }`; templates and creatures add `template` and so on. Same-id rules replace in place (position is priority, so a replacement keeps its slot), **new rules go ahead of every rule from more general layers** (keeping their order within the layer), `disable` switches rules off (a later layer supplying the id re-enables it), policies merge by key (`null` removes), slot bindings merge with the more specific layer winning. Templates do not extend other templates in v1.
- **Why new rules go first (found while building the starter templates):** rule order is priority, and the shipped `fallback-strikes` rule (always true) sits last in the system layer. Appending template rules after it meant a template's "Volley" could never outrank "Strike, strike", and system rules like `close-in` would have beaten an Archer's own rules. More specific layers now rank ahead of general ones; an explicit `priority` still overrides position. Consequence: creature and template rules outrank shipped defaults such as `last-stand`; set `priority` (lower first) on a rule, or disable the default, to change that.
- **Slots:** derived from the `do` lists of enabled rules (plus any declared), excluding movement (`stride`, `stride-away`). Strike slots auto-bind to the first matching strike in `actor.system.actions`; other slots are never guessed. A GM binding (`slotBindings`: slot to item id) always wins. A rule needing a strike slot the creature cannot fill is **held back** (the creature lacks that attack); other unbound slots only **warn** and the rule stays with a generic label.
- **Storage (V6, as built):** creature profile in a flag on the base actor (shared by all tokens); encounter overrides in a combatant flag; templates and campaign in world settings. Layers are replaced by unset-then-set, because flags merge on write.
- **Validation (partial):** unknown condition, unbound or missing slot binding, empty `do`, `oncePerEncounter` with other limits, unknown disable target, duplicate id in a layer, missing template. Not yet: unreachable rules.
- **Expanded card (build step 7):** the strip collapses to one line (name, suggestion, pips, Took it, expand). Expanded shows template and round, the primary suggestion with actions/target/hint, one alternative, "Took suggestion" and "Something else", this turn's log with add/remove, and collapsible "Why this one", "Held back (n)" and "Warnings (n)". The engine returns up to three suggestions; "Something else" cycles through them and resets whenever the evaluation context changes. Expanded state and open sections are remembered (client setting / in memory). `hint` is an optional string on a rule.
- **Target selection (build step 4):** a selector is an ordered preference list applied lexicographically (`engine/targets.mjs`): `role:<tag>` (holders first), `lowest-hp`, `highest-hp`, `nearest`, `farthest`; ties keep original order; unknown entries are ignored and warned about. So `["role:caster","lowest-hp"]` is casters first then lowest HP, while `["lowest-hp","role:caster"]` lets the tag only break ties. If no enemy has a preferred tag, selection falls through to the next preference. Enemy conditions narrow candidates first, then the selector picks. Default selector when a rule narrows without one: `lowest-hp`.
- **Every suggestion names a target (supersedes the brief's section 7 "action only" fallback, at the GM's request):** a rule with no `target` preferences uses `DEFAULT_SELECTOR` (in reach first, then lowest HP) and the card says "(default)". A rule with no enemy to pick is held back as "no valid target", so with no enemies there is **no suggestion** and the strip says "No enemies to target" (an empty enemy list can also mean the adapter found no hostile combatants, e.g. an alliance mismatch). Movement rules name who the creature moves relative to: Coward's Flee and Panic target the nearest enemy, "the one it is fleeing from". Every shipped default rule and every starter rule declares its own target (tests enforce it), so the default is a safety net for hand-written rules, not something the shipped rules lean on. The editor says a target is always named and shows the default in a rule's sentence.
- **Role tags (resolves the initial-list [OPEN]):** free-form lowercase strings; suggested list: caster, healer, squishy, frontliner, ranged, support. Campaign default is a flag on the PC's base actor; the encounter override is a flag on the combatant and **replaces** the default for that combat (an empty list clears it). `null` removes the override.
- **`in-reach` selector entry:** `enemy-in-reach` stays a global any-enemy check (the brief's `retreat-and-shoot` shoots a target who may not be the adjacent one), so melee rules use the `in-reach` target preference instead (in-reach enemies first, then the next preference). Narrowing by reach was considered and rejected because it would make a ranged retreat rule target the adjacent enemy.
- **Starter templates (build step 8, part 1):** ten fighting styles in `engine/starter-templates.mjs`, **named for how the creature fights, not for its job in the encounter** (the brief's first list, Brute/Skirmisher/Archer/Caster/Skittish, mixed the two): Brawler, Berserker, Duelist, Skirmisher, Ambusher, Sniper, Spellslinger, Hexer, Coward, Swarmer. They use only the v1 vocabulary and are starting points to tweak. Each description states what it needs bound. The four renamed ones keep working under their old ids through `STARTER_ALIASES` (brute, archer, caster, skittish); a world copy under an old id still wins. Rule ids are prefixed with the template id and unique across templates (a test enforces it), so renamed templates' rule ids changed (e.g. `archer-volley` is now `sniper-volley`); this only affects rule-use history of combats already in progress. Lookup precedence: your world templates beat starters of the same id; `installStarterTemplates()` copies starters into the world for editing; `listTemplates()` shows the source of each. A test confirms every template yields at least one suggestion in three scenes (nobody around, one far enemy, one adjacent enemy).
- **Known limitation of the starter set:** several melee styles only act on enemies within a range (Duelist 25 ft, Berserker/Swarmer/Ambusher 60 ft). Beyond that no style rule fires and the shipped "Strike, strike" fallback shows with no target. That is honest (nothing better is known) but could read oddly; a "no good option" fallback is a possible later refinement. Likewise `enemy-has-condition` rules (Duelist's off-guard, shipped `punish-prone`) narrow to affected enemies but cannot require that they are in reach; the `in-reach` preference handles the common case.
- **Dry run:** `dryRun(actorOrName, { round = 1, token, print = true })` evaluates a creature with no combat: enemies are the visible hostile tokens on the current scene, history empty, full action budget. Notes explain anything limiting the answer (no token, no hostile tokens, no alliance). Distances are unknown without a token, so reach and distance rules will not fire.
- **Context shape:** `{ round, self: { name, hpPercent, conditions[] }, enemies: [{ id, name, hpPercent, conditions[] }] }`, built by `scripts/adapter.mjs`. Defined in `scripts/engine/conditions.mjs`.
